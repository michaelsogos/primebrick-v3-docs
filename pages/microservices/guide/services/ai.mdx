The AI microservice provides an in-app chat assistant that answers questions
about Primebrick using RAG (Retrieval-Augmented Generation). It embeds
documentation into a pgvector knowledge base, retrieves relevant chunks at
query time, and streams responses from a local or cloud LLM.

- **Package:** `primebrick-ai`
- **Service code:** `AI`
- **Default port:** `3004`
- **Runtime:** Bun (dev: `bun --hot`, prod: `bun dist/index.js`)
- **Database schema:** `ai` (isolated per-service schema)
- **Vector extension:** pgvector (cosine similarity, HNSW index)

## Components

### RAG pipeline

The RAG (Retrieval-Augmented Generation) pipeline powers documentation-aware
answers:

1. **Embedding**: The user's query is embedded using
   `Xenova/all-MiniLM-L6-v2` (384-dim, CPU/WASM via Transformers.js).
2. **Vector search**: The embedding is compared against `ai.docs_kb` using
   pgvector cosine distance (`<=>` operator) with an HNSW index.
3. **Context injection**: The top-k chunks are injected into the LLM prompt
   as context.
4. **LLM response**: The LLM generates an answer grounded in the retrieved
   documentation.

### MCP client integration

The orchestrator connects to the Backend's MCP server
(`{BE_BASE_URL}/mcp`) using Streamable HTTP transport with the user's JWT.
This gives the LLM access to generic CRUD tools:

- `list_available_entities` — list all entities the user can query
- `list_entities` — list/search/aggregate records
- `get_entity` — get a single record by UUID
- `get_entity_meta` — get entity field metadata
- `get_entity_audit` — get audit history for a record

### Local search_docs tool

In addition to MCP tools, the orchestrator registers a local `search_docs`
tool that searches the RAG knowledge base directly. The LLM calls this tool
when the user asks about framework architecture, APIs, configuration, or any
topic covered by the documentation.

### PII redaction

When `REDACT_PII=true` (recommended for cloud LLMs), the orchestrator
redacts personally identifiable information from messages before sending
them to the LLM:

- Emails → `[EMAIL_1]`, `[EMAIL_2]`, ...
- Phone numbers → `[PHONE_1]`, ...
- Credit card numbers → `[CARD_1]`, ... (with Luhn validation)

Original messages with real PII are persisted to the database unchanged.
Only the LLM sees the redacted version.

## HTTP routes

All routes are proxied by the Backend via `/ws/ai/*`. Authentication is
handled by the gateway (headers: `x-user-id`, `Authorization: Bearer <jwt>`).

| Method | Path | Purpose | Auth |
|--------|------|---------|------|
| GET | `/api/v1/ai/health` | AI health check (LLM connectivity + model info) | Gateway |
| POST | `/api/v1/ai/chat` | Chat endpoint with SSE streaming | Gateway + rate limit |
| GET | `/api/v1/ai/conversations` | List user's conversations | Gateway |
| POST | `/api/v1/ai/conversations` | Create new conversation | Gateway |
| GET | `/api/v1/ai/conversations/:uuid` | Get conversation with messages | Gateway |
| PATCH | `/api/v1/ai/conversations/:uuid` | Update conversation title | Gateway |
| DELETE | `/api/v1/ai/conversations/:uuid` | Delete conversation | Gateway |
| POST | `/api/v1/ai/feedback` | Submit thumbs up/down on a message | Gateway |
| GET | `/api/v1/ai/feedback` | List user's feedback | Gateway |
| GET | `/api/v1/ai/telemetry` | Aggregate stats + recent requests | Admin only |
| POST | `/api/v1/ai/reindex` | Trigger embedding pipeline | Admin only |

### Chat endpoint

`POST /api/v1/ai/chat` streams the response via Server-Sent Events (SSE).

**Request body:**

```json
{
  "message": "How does RBAC work?",
  "conversation_uuid": "optional-uuid-for-existing-conversation"
}
```

**SSE events:**

| Event | Payload | Description |
|-------|---------|-------------|
| `text-delta` | `{ text: string }` | Partial text chunk |
| `tool-call` | `{ toolName, input }` | LLM invoked a tool |
| `tool-result` | `{ toolName, result }` | Tool returned a result |
| `client-tool-call` | `{ toolName, input }` | Frontend must handle (e.g. navigate) |
| `finish` | `{ text, tokensIn, tokensOut, steps }` | Stream complete |
| `error` | `{ message }` | Error occurred |

### Rate limiting

The chat endpoint uses a token bucket algorithm per user (identified by
`x-user-id` header). Configuration:

| Variable | Default | Description |
|----------|---------|-------------|
| `AI_RATE_LIMIT_CAPACITY` | `10` | Max tokens in bucket per user |
| `AI_RATE_LIMIT_REFILL_RATE` | `1` | Tokens refilled per second |
| `AI_RATE_LIMIT_TOKEN_COST` | `1` | Tokens consumed per chat request |

If `REDIS_URL` is set, rate limiting is distributed across instances.
Otherwise, an in-memory token bucket is used (single-instance only).

## Embedding pipeline (indexing)

The embedding pipeline populates `docs_kb` from the documentation source
files. Run it with:

```bash
cd ai && pnpm run index-docs
```

**Flow:**

1. **Load docs** from `DOCS_PATH` (MDX files) and `OPENAPI_PATH` (JSON specs)
2. **Chunk** each doc (sentence-aware, ~1800 chars, 200 char overlap)
3. **Compute SHA-256** for each chunk (incremental re-indexing)
4. **Skip unchanged chunks** (content_hash matches DB)
5. **Batch embed** changed chunks (batch size 16) via the embedding provider
6. **Upsert** into `docs_kb` (ON CONFLICT update)
7. **Delete stale chunks** (docs removed from source)

The pipeline is idempotent — re-running it only re-embeds changed chunks.

## LLM runtime

The default LLM is a local mistral.rs container running
Qwen3-4B-Instruct-2507 (Q4_K_M quantization). See the Backend's
`infra/docker-compose.ai-llm.yml` for the container configuration.

The LLM provider is pluggable — any OpenAI-compatible endpoint works
(OpenAI, Anthropic via proxy, DeepSeek, Groq, etc.) by changing
`LLM_BASE_URL`, `LLM_API_KEY`, and `LLM_MODEL`.

## Local development

### Prerequisites

1. PostgreSQL with pgvector (from `infra/docker-compose.postgres.yml`)
2. LLM container (from `infra/docker-compose.ai-llm.yml`) or a cloud LLM
3. Backend running on port 3001 (for MCP client)

### Steps

1. Copy `.env.example` to `.env` and adjust values
2. Apply migrations: `pnpm run db:migrate`
3. Index docs: `pnpm run index-docs`
4. Start dev server: `pnpm run dev`
5. Verify health: `curl http://localhost:3004/health`
